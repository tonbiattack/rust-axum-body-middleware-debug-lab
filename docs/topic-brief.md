# 題材企画: 監査ミドルウェアがJSON APIのボディを消費する

## 対象

| 項目 | 内容 |
| --- | --- |
| 対象言語 | Rust 1.75.0 |
| 対象読者 | AxumでJSON APIとミドルウェアを実装し、HTTP 400の原因を境界テストで切り分けたい開発者 |
| 難易度プロファイル | 実践・上級 |
| 選定理由 | HTTP 400、監査ログ、ハンドラー未到達という複数の観測を、リクエストボディの一回限りの消費まで絞り込むため |
| 実行基盤 | Cargo、Axum 0.7、Tokio、Towerの`oneshot` |
| API境界 | `POST /tasks`へのJSONリクエストを、実サーバーを起動せずルーターへ送る統合境界 |

## 学習する契約

> `POST /tasks`に`application/json`の有効なJSONを送り、監査ミドルウェアを通過した場合、期待する応答と状態は`201 Created`および作成済み件数1である。バグ状態では`400 Bad Request`および作成済み件数0になる。

### 対象の直接原因

監査ミドルウェアが`to_bytes`でリクエストボディを消費した後、`Body::empty()`を再構築して次のハンドラーへ渡していることです。`Json`抽出器はボディを消費してデシリアライズするため、空のボディではJSON拒否応答になります。

### 対象外

認証、CORS、ストリーミングアップロード、監査ログの秘匿化、ボディ上限のポリシー、実DBへの保存は扱いません。

## 再現設計

| 要素 | 決定 |
| --- | --- |
| 公開境界 | `Router`へ`tower::ServiceExt::oneshot`で送る`POST /tasks` |
| 入力・初期状態 | `Content-Type: application/json`、タイトルを含む有効JSON、作成済み件数0 |
| Redの観測 | 応答が`400 Bad Request`、作成済み件数が0であるため契約テストが失敗する |
| 最終観測 | HTTPステータスと、`AtomicUsize`で管理する作成済み件数を独立して確認する |
| 決定性 | インメモリのルーターと状態だけを使い、ネットワーク・時刻・任意の待機を使わない |
| 固定状態の検証コマンド | `cargo test -- --nocapture` |
| バグ状態の確認コマンド | `cargo test json_post_must_reach_handler_after_audit_middleware -- --nocapture` |

## 仮説

| 仮説 | どう検証または除外するか |
| --- | --- |
| 監査ミドルウェアがボディを消費している | 監査ログにバイト数が出た後、`Json`抽出器の手前で空ボディを作るコードを確認する |
| リクエストのJSONまたはContent-Typeが不正である | テストで有効JSONと`application/json`を固定し、ミドルウェアを通る場合だけ400になることを確認する |
| ハンドラー内の状態更新が失敗している | 応答ステータスと作成済み件数を分けて確認し、ハンドラーログが出ないことを確認する |

## 予定と実績の履歴
